# Sajilo Yatra API contract
All records come from PostgreSQL. All mutations require the configured APP_ORIGIN Origin header except the bearer-authenticated expiration job. JSON errors have {error, requestId}. Validation errors use 400, unauthenticated 401, unauthorized 403, absent or foreign private records 404, conflicts 409, throttling 429 (only when RATE_LIMITS=on), database or upstream outages 503 with Retry-After. No endpoint ever answers 500. Lists use page (1 based), 25 rows and nextPage. Times are ISO UTC; display in Asia/Kathmandu. Money is integer NPR.

GET /api/health returns 200 {status:"ready",database:"up",schema:"up"} only when PostgreSQL and the application schema are usable; otherwise it returns 503 {status:"degraded",database:"down"}.

GET /api/trips?origin=&destination=&date=YYYY-MM-DD&page= returns public trip details, the matched journey (stop indexes), its fare and available seat count. GET /api/trips/:id[?from=&to=] returns public vehicle, current driver name, stops, boarding/drop-off points, seat coordinates and server-derived AVAILABLE/HELD/BOOKED/BLOCKED inventory for the journey. GET /api/locations lists places. GET /api/site-content returns the editable website text.
POST /api/bookings {tripId,seats:[tripSeatId],name,phone,email?,idempotencyKey,fromLocationId?,toLocationId?,boardingPointId?,dropPointId?} holds 1–8 seats for the configured minutes, returns 201 {id,reference} and sets the private HttpOnly cookie booking_{id}. idempotencyKey must be a random 32+ character secret; replaying it returns the same booking, replaying it with different data is 409. No price is accepted from the client.
GET /api/bookings/:id requires its capability cookie. POST /api/bookings/:id/proof multipart {image,claimedAmount,method,transactionRef?,remarks?} requires capability and a valid unexpired hold, stores the re-encoded private proof and starts the review window. POST /api/bookings/:id/clarification {message} while under review or in reconciliation. GET /api/bookings/:id/ticket returns a signed ticket once confirmed and verified.
POST /api/track/request {reference,phone} always returns a challenge ID without confirming existence; the code goes to the booking email (SMTP) or phone (SMS). In development without either channel the code is printed to the server console. POST /api/track/verify {challengeId,code} consumes the single-use five-minute code, rotates the booking capability and sets the cookie.
POST /api/auth/login {role:ADMIN|DRIVER,email,password}; POST /api/auth/logout. Database sessions expire after 12 hours. Wrong passwords never lock an account.

Driver owners: GET /api/admin/owners lists the private internal owner of each driver, for choosing who a record belongs to. POST /api/admin/drivers creates the driver together with that owner.
Admin modules: GET/POST/PATCH /api/admin/:resource and DELETE /api/admin/:resource/:id for vehicles, drivers, locations, routes, fares, trips, payment-qr; GET/PATCH settings; GET bookings, payments. POST creates (tenant records need operatorId), PATCH requires id. DELETE is refused with 409 while trips, bookings or payments reference the record. Seat layouts: GET/POST/PATCH /api/admin/seat-layouts, POST .../:id/publish|archive, DELETE .../:id (drafts only). A layout cell may be `door-seat`; it is both a required door marker and normal bookable seat inventory, so normal route and vehicle fares apply. Route stops and points: GET /api/admin/route-points/:routeId, POST/PATCH /api/admin/route-points, DELETE /api/admin/route-points/:id. Segment fares: GET /api/admin/segment-fares/:routeId?vehicleType=, PATCH /api/admin/segment-fares {routeId,vehicleType,fromLocationId,toLocationId,amount|null}. Also GET catalog, reports, audit?targetId=, vehicle-profile/:id, PATCH trip-seats {tripSeatId,blocked,note}, POST reconciliation, POST payments/:id {action:verify|reject|clarify,note,bankEvidence?,verifiedAmount?,confirm?,acknowledgeDuplicate?}, POST manual-bookings, POST uploads multipart {image,purpose:qr|vehicle|driver|site}, GET/PATCH site-content.
Driver self-service: GET/PATCH /api/driver/profile, POST /api/driver/password, GET /api/driver/fleet, POST /api/driver/submissions {kind:vehicles|routes|payment-qr,targetId?,payload}, DELETE /api/driver/submissions/:id, POST /api/driver/trips, POST /api/driver/trips/:id/cancel {reason}, POST /api/driver/uploads. Long-term schedules: GET/POST /api/driver/schedules; POST accepts {startsOn,endsOn,plans:[{routeId,vehicleId,paymentQRId,departureTime,fare?}]}, creates separate dated trips; PATCH /api/driver/schedules/:id accepts {action:pause|resume|cancel|extend,endsOn?}. Review: GET /api/admin/driver-submissions?status=, POST /api/admin/driver-submissions/:id {action:approve|reject,note}.
Drivers: GET /api/driver/trips[/:id], GET /api/driver/passengers?tripId=, POST /api/driver/check-in {passengerId,status:CHECKED_IN|BOARDED}, POST /api/driver/validate-ticket {ticket}, POST /api/driver/issues {tripId,note}. Drivers cannot verify payments.
GET /api/images/:objectId serves object data (proof: booking owner or admin; other images: public). Objects live in S3 when configured, otherwise under STORAGE_DIR. POST /api/jobs/expire requires Authorization Bearer CRON_SECRET; idempotent serializable transactions release non-confirmed claims, preserve evidence and deliver queued notifications.
